# GridMate 改造版代码审阅

审阅日期：2026-11-16。对象：`C:/Users/xiaohe/WorkBuddy/实习/GridMate` 当前工作目录，不代表 GitHub 上的版本。

## 结论与验证范围

停电台账问数与相似事件检索的方向值得继续。按度量粒度聚合、参数化 SQL、混合检索和重排都有具体实现；事件聚合也已经补上性质、供服中心的多值明细与冲突标记。

当前仍有可以稳定复现的正确性问题，集中在查询条件、时间边界、证据传递、失败处理和评测标准答案。它们不是换一个更强模型就能消除的问题。建议先完成下面这些修复，再扩展功能。

本次执行了本地 SQLite 只读核对、模拟工具/Agent 调用、评测器反例和 Python AST 语法检查。28 个 Python 文件语法检查通过。没有调用外部模型、Embedding、Reranker 或 Milvus，没有验证完整 HTTP/网页端到端链路；因此不据此宣称整套服务全部正常。本次只新增审阅文档，没有修改业务代码。

## 1. 高优先级：线路与时间等组合条件会丢失

位置：`app/core/ask.py:47`、`:215`、`:240`；`app/core/query_templates.py:34`。

四个模板分别处理线路、供服中心、时间段、全局性质占比，但没有支持它们的组合。即使意图里同时有线路和时间，`_validate()` 也会通过，`_to_params()` 随后只保留选中模板的参数。

本地复现：构造“线路32、2025-06-01 至 2025-07-01”的线路统计意图，校验通过，实际参数仅剩 `{"line_name": "线路32"}`。数据库中这条线路全样本有 8 个事件，6 月为 0 个事件。现有模板无法正确执行这个组合查询。自然语言是否选到某个模板取决于模型，本次没有对真实模型做此断言。

README 的“那这条线今年6月呢”正好依赖这项缺失能力，指代消解成功并不等于后续统计正确。

建议：将“指标”和“过滤条件”分开建模，在白名单内组合线路、中心、时间、性质条件；暂未支持的组合明确返回不支持/澄清，不能静默忽略。增加线路与月份交叉、中心与月份交叉的固定预期用例。

## 2. 高优先级：月末、年末少算，且相对年份被改写

位置：`app/core/ask.py:125`；`app/core/query_templates.py:57`；`app/core/agent.py:50`。

SQL 使用 `[start_time, end_time)`，但提示词把 6 月终点写为 6 月 30 日，全年终点写为 12 月 31 日。这会排除最后一天。

本地只读结果：

| 查询范围 | 去重事件数 |
|---|---:|
| `[2025-06-01, 2025-06-30)` | 159 |
| `[2025-06-01, 2025-07-01)`，完整 6 月 | 160 |
| `[2025-01-01, 2025-12-31)` | 1998 |
| `[2025-01-01, 2026-01-01)`，完整 2025 年 | 2000 |

另外，代码要求“今年”和“去年”都解析为 2025 年。以本次审阅日期为准，今年应为 2026 年。数据只有 2025 年不意味着可以替用户改掉年份。

日期校验只有正则和字符串比较，本地构造 `2025-02-30` 至 `2025-03-02` 也能通过。

建议：用日期库生成次月首日/次年首日并验证日期；相对时间使用明确参考日期，或在界面明确设置查询年份。用户要求数据覆盖外的年份时返回覆盖范围不足，不能当作有完整数据的零次结果。

## 3. 高优先级：评测标准答案使用了被测系统的参数，错问题也能通过

位置：`scripts/eval_ask_extended.py:83`。

评测器用 `r['intent']` 中的线路、中心、时间去算参考值。SQL 虽然单独写了一遍，但如果模型把线路 A 解析成 B，双方都会按 B 计算，仍能通过。这验证了执行结果是否符合模型参数，没有充分验证是否符合用户原问题。

本地反例：题目为“2025年6月完整月份一共停电多少次”，模拟被测系统返回少一天的区间和 159 次。现有评测器的 `template_ok`、`status_ok`、`fact_ok` 全部为 `true`，而完整月份正确结果为 160。

性质占比评测还只比较结果行数/种类数，没有比较每类次数及百分比。因此报告中的“数字正确 30/30”不能解释为 30 个用户问题的端到端答案全部正确。

建议：每道题保存独立确认的预期指标与过滤条件，先校验解析结果，再按预期条件计算参考值；占比逐类比较分子、分母、百分比。补充从实际 Agent 工具输出到最终答案的检查。原始评测结果可保留，但应收窄其结论，修复后重新评测。

## 4. 高优先级：回答模型看不到完整证据

位置：`app/core/tools.py:51`、`:82`；`app/core/ask.py:254`。

相似检索底层已经返回事件正文、多值明细和冲突标记，但工具封装只传事件号、性质、电压、截断线路、日期和重排分。具体故障对象、原因、处置文字都被丢掉了。

本地模拟：底层返回“测试电缆绝缘损坏，已更换电缆”及性质冲突标记，调用 `search_similar_events` 后，工具文本中不含正文，也不含冲突。模型因此无法据此回答具体原因或处理方式；忠实度评审收到的也只是同一份不完整证据。

统计工具同样只传一句摘要。性质占比查询虽然有多行结果，摘要只保留类别总数与占比最高的一类，回答模型无法得知其余类别的具体占比。

建议：工具返回结构化证据，至少包含完整统计行、实际过滤条件、事件 ID、相关正文片段、来源及冲突信息。长度控制应按证据相关性裁剪，不能只留下分类标签。

## 5. 高优先级：忠实度检查失败后仍正常返回答案

位置：`app/core/agent.py:110`、`:167`；`app/core/faithfulness.py:13`。

`run()` 只记录 `faithful` 和原因，无论检查是否通过都返回原答案；`chat()` 又将该答案写入历史。

本地模拟：Agent 返回合成错误答案“停电999次”，检查器明确返回 `faithful=False`。原答案仍被返回，并出现在下一轮可读取的会话历史中。

这与代码注释中的“宁可判不忠实也不放行”不一致。目前它是告警标记，不能描述为答案拦截机制。README 还声称有生成前 selfcheck，但当前目录没有对应模块，主链路也没有看到该步骤。

建议：检查失败后有限次数重新生成；仍失败则返回可验证的工具事实或说明证据不足。未通过答案不能作为已确认事实进入历史。检查器异常可单独标为“未验证”，不要与确定不忠实混为一谈。README 按实际实现调整。

## 6. 高优先级：性质占比口径不互斥，总和达到 108.65%

位置：`app/core/query_templates.py:69`；`scripts/query/build_event_corpus.py:102`。

本地数据共有 2000 个不同事件序号，其中 165 个对应多个停电性质。按性质分别去重后，类别次数相加为 2173，各类百分比总和为 108.65%。

同一个事件属于多个类别本身未必是错误；问题是系统没有说明多标签覆盖率，却以通常会被理解为互斥分布的“各类占比”提供结果。语料侧的主性质/冲突标记也没有统一进入统计口径。

建议：先确认原台账事件序号的业务唯一性，以及一事件多性质是否合理。若采用多标签统计，明确类别重叠、总和可超过 100%；若需要互斥分布，制定可解释的归类/冲突处理规则。不要仅为凑到 100% 而随意取首值或改分母。

## 7. 高优先级：脱敏正则破坏技术语义，发布排除规则也有缺口

位置：`scripts/data_prep/sample_and_mask.py:156`；`.gitignore:11`。

道路地址正则会把包含“路”的普通技术词一起替换。通过提取当前源码中的脱敏常量和函数，在合成文本上复现：

| 输入 | 当前输出 |
|---|---|
| 断路器故障 | 某路器故障 |
| 线路检修 | 某路检修 |

这会直接损坏检索语料，尤其影响需要区分设备对象的相似判断。

仓库内评测报告还承认 v2 标注文本存在姓名/门牌残留，因此不能将“文件位于 masked 目录”等同于可以公开。当前 `.gitignore` 的 `data/*.db*` 不覆盖 `data/masked/gridmate.db`；只读 Git 检查显示它尚未被跟踪，也没有命中忽略规则。语料和 CSV 同样未排除。这里是可误提交的缺口，不是已经发布泄露的证据。

建议：优先按已知实体映射替换并保留电力术语，地址规则要求更明确的地址上下文。修复后重新生成语料、向量和标注候选。公开仓库只放经检查的合成示例；本地真实数据、含原文的标注文件和报告显式排除。

## 其他应明确的边界

1. **统计与相似检索没有共享过滤范围。** `app/core/similar.py:65` 的检索请求没有线路、中心、日期硬过滤。问“某线路某月的相似案例”时，单靠自然语言进入向量检索不能保证返回范围正确。建议复用统计过滤结构，或明确提示这是全库相似案例。
2. **P@5 的指标名称需修正。** 报告中 36/50=72% 是待复核按不相关时的保守结果；36/42≈85.7% 是已明确标签上的相关比例，不是完整 Top-5 的 P@5。8 个未决项对应的整体范围为 72%～88%，且标签属于 AI 初审。`eval_similar_compare.py` 还按 query 对明确比例做平均，与报告直接按 36/42 合并不是同一种聚合方法，应统一。重排分升高本身也不等于检索正确率提升。
3. **自动回归用例不足。** 当前 `tests` 下未发现 `test_*.py`，主要是评测数据文件。优先补上本文已复现的日期边界、组合过滤、证据保留、失败答案处理和评测反例，不必恢复全部旧客服测试。
4. **本地依赖未完全同步。** 当前虚拟环境直接导入数据脱敏脚本报缺少 `openpyxl`，虽然它已在 `pyproject.toml` 声明。本次用 AST 提取纯脱敏函数验证，没有安装依赖或运行原始数据处理。README 应补依赖安装/同步、数据库构建、Milvus 索引初始化步骤。
5. **统计范围需要说明。** 当前库是抽样后的 2000 个事件。回答中的“总次数、总缺供电量”等应明确为当前样本台账范围，不能自然延伸为完整业务台账或地区年度总量。

## 建议修改顺序与验收

1. 先修评测标准答案与日期边界，固定上述 159/160、1998/2000 反例。
2. 支持或明确拒绝组合过滤，并让统计和检索共享范围。
3. 保留完整证据，落实忠实度失败后的降级处理。
4. 确认多性质事件的业务口径，修复脱敏规则并重建衍生数据。
5. 用小规模、覆盖真实失败模式的独立题集复测，更新 README 和评测报告。

在这个阶段，无须为了增加技术名词而继续引入新框架。把这些真实问题修好、保留失败样例与前后验证记录，会比扩充演示功能更有利于面试讲解。
