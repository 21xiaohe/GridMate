# GridMate 与 Quarry-RAG 整合建议

日期：2026-11-16

本文是基于两个本地项目源码的整合建议，不代表已经实施，也不代表已验证两个服务联通。优先级针对当前停电台账问数场景与大模型应用开发实习求职目标。

## 一、结论

可以整合。推荐保留 GridMate 的业务主线、SQLite 统计库和 Milvus 检索库，选择性吸收 Quarry 的证据结构、索引更新机制、检索不足信号与评测方法。

当前最有价值的目标是：**让用户问题中的条件、SQL 统计范围、检索案例范围、最终回答证据和评测预期保持一致。**

暂不建议整体迁移到 Quarry 的 PostgreSQL + pgvector + Redis 架构。GridMate 已有混合检索与重排，迁移会增加数据适配、部署和重新评测成本，不能据此保证检索效果提升。

## 二、两个项目如何分工

| 模块 | 职责 | 整合建议 |
|---|---|---|
| GridMate 问数 | 识别指标与条件，通过参数化 SQL 计算次数、电量和占比 | 保留，继续加强时间和统计口径校验 |
| GridMate 相似事件检索 | 从事件备注中召回、重排历史案例 | 保留现有底座，吸收 Quarry 的证据契约和范围约束设计 |
| GridMate Agent | 选择工具、组织答案、处理澄清与失败 | 保留，消费统一证据，避免丢失范围和冲突信息 |
| Quarry 证据层 | 返回正文、上下文、来源定位、分数与拒答建议 | 按停电事件的数据形态改造后复用 |
| Quarry 索引和评测 | 幂等接入、旧块清理、逐题评测、回归对比 | 借鉴实现原则，适配 Milvus 和事件级标签 |

建议的最小结构：

```text
用户问题
   ↓
问题理解／指代消解：保留原始问题，统一时间参考与实体条件
   ↓
GridMate Agent
   ├─ 统计工具 → 校验指标与条件 → SQLite → 统计证据
   └─ 检索工具 → 校验范围 → Milvus 混合检索与重排 → 案例证据
   ↓
统一证据：实际范围、数据版本、来源定位、冲突／不足状态
   ↓
回答生成 → 忠实度检查 → 正常回答／澄清／降级
```

这不是新增一个大型平台，而是把现有工具间的数据交接做完整。

## 三、优先复用的四项能力

### 1. 统一证据结构

Quarry 将检索结果组织为 Evidence，区分命中正文、提供给模型的上下文、引用定位和检索分数。GridMate 可以沿用这种分层思想，但要增加停电业务字段。

建议统计与案例证据共享以下公共字段：

- `request_id`：关联本次查询、日志与回答。
- `dataset_version`：表明本次使用的数据版本。
- `requested_filters`：用户请求的条件。
- `effective_filters`：实际执行的条件。
- `coverage_status`：完整覆盖、部分覆盖或范围外。
- `warnings`：属性冲突、缺失数据、未支持条件等明确说明。

统计证据再包含：指标、单位、统计粒度、模板ID、全部结果行，以及占比的分子和分母。单位应来自数据字典，不能凭经验补填。

案例证据再包含：事件ID、来源记录ID、相关正文、事件属性、多值明细、冲突标记、实际采用的时间口径和各路检索分数。

**关键规则：** 结构化对象在模块之间完整传递，仅在给模型或页面展示时渲染成文本。忠实度检查使用与回答生成相同版本的证据，不能重新拼出一份遗漏字段的摘要。

### 2. 可靠的索引更新

Quarry 的索引代码中有“先准备数据与向量，再在事务中写入并清理旧块”的设计。可以借鉴它避免半成品替换可用数据的原则。

但 PostgreSQL 事务不能直接搬到 Milvus。GridMate 建议采用：

1. 生成带版本号的数据与事件语料。
2. 校验事件标识、字段、文本、向量条数和向量维度。
3. 将向量写入新的版本集合，保留当前可用集合。
4. 校验新集合的行数、样例检索和版本信息。
5. 验证通过后切换检索别名，失败则继续使用旧集合。
6. 保留至少一个可回退版本，之后再清理旧集合。

SQLite 与 Milvus 的切换还要协调：单次请求应使用同一个已发布的数据版本。可以通过版本清单和维护窗口发布实现，不必引入分布式事务。SQLite 切换后同步刷新线路词典与占比分母缓存，或明确重启服务。

事件业务ID与内容版本应分开：修改备注不应让业务事件失去身份；事件ID的唯一性范围必须先确认。内容哈希用于判断哪些内容变化，不能自动解决不同记录是否属于同一事件的问题。

### 3. 检索不足与冲突信号

Quarry 会给出“建议拒答”的结构化信号，最终是否回答由上游决定。GridMate 可以增加类似能力，并结合业务条件细分：

| 情况 | 建议行为 |
|---|---|
| 指定范围内没有候选 | 说明该范围内未检索到相关记录 |
| 候选存在，但相关性证据不足 | 说明无法确认相似，避免硬推荐 |
| 事件属性存在冲突 | 展示冲突及相关原文，不擅自选定结论 |
| 请求时间只被部分覆盖 | 明确实际覆盖区间，必要时先澄清 |
| 检索或评审服务异常 | 标记未验证或暂不可用，不混同于没有事件 |

不要直接复用 Quarry 的默认分数阈值。Embedding 模型、语料、检索策略改变后，分数分布也会变化，必须使用停电场景的相关与不相关样例重新校准。

这个步骤与生成后忠实度检查互补：前者判断证据是否足够，后者检查回答是否超出已有证据。两者都不能代替用户意图和过滤条件的正确性校验。

### 4. 固定题集与逐题回归对比

借鉴 Quarry 的逐题结果、延迟记录和版本对比，将 GridMate 的评测拆为三个层次：

| 层次 | 核对内容 |
|---|---|
| 问数 | 指标、所有过滤条件、覆盖范围、统计值、单位与口径 |
| 检索 | 相关事件是否返回、是否满足范围、排序、重复事件、误拒与漏拒 |
| 完整回答 | 是否回答原问题、数字与引用是否对应、冲突和部分覆盖是否明确说明 |

现有只有Top-5候选的标注，适合分析这些候选的相关性；没有足够完整的相关事件集合时，不应把结果写成全库Recall@K。

AI初审、人工确认和待复核标签应分开保留。36/42是已明确标签上的相关比例，不能命名为完整Top-5的Precision@5。

每次评测保存问题集版本、数据版本、模型及检索配置。比较整合前后效果时使用同一份题集；开发集用于调参，验收题尽量固定。至少加入无结果、范围外、部分覆盖、冲突、索引更新失败和检查器异常等失败场景。

## 四、最值得作为主线的业务示例

用户问题：

> 线路32在2025年6月停电多少次？有没有该线路同期的电缆故障记录？

系统应当：

1. 统计工具按线路与完整月份查询，月份区间采用`[2025-06-01, 2025-07-01)`。
2. 检索工具使用相同线路和经过定义的时间过滤语义，再进行语义检索。
3. 数字附统计口径；案例附事件与来源记录定位。
4. 没有该范围内的案例时明确说明，不能拿其他线路或其他月份的事件补上。
5. 不把Top-K返回条数当成故障发生总次数，也不根据相似案例推断本次停电的确定原因。

若用户说的是“其他线路有没有类似情况”，应明确按另一个检索范围执行并展示，不能机械地要求所有工具条件永远相同。重点是符合用户分别提出的范围。

建议先把演示问题限定为这些有清晰答案和口径的场景，避免扩展到尚无数据或领域依据的故障预测、调度决策和处置建议。

## 五、不能直接照搬的内容

### 元数据过滤不等于日期范围查询

Quarry 当前混合检索SQL中的元数据过滤主要是JSON包含匹配。它可以作为属性过滤设计的参考，但没有现成的停电日期区间语义。

GridMate 需要明确事件时间究竟按最早开始、任一用户开始时间，还是与查询区间重叠来判断，再让SQL统计与检索过滤采用一致或明确区分的口径。多线路事件也不能只用截断后的线路字符串匹配。

### 文档字符引用不等于台账行引用

Quarry 的引用定位是文档字符区间。GridMate 的台账记录更适合使用：

```text
数据集版本 + 来源表/文件标识 + 来源行ID + 事件ID
```

来源行ID需要在导入时保留或稳定生成，不能默认SQLite每次重建后的自增ID都代表同一条来源记录。事件正文由多条备注合并时，应保留各片段到来源行的映射，不能把整段合并文本说成一条原始记录。

### 旅游事实核实层不适合直接处理停电指标

Quarry 中的门票价格、开放时间抽取和官方值替换具有旅游业务假设。GridMate 的次数、电量等应来自台账确定性查询。不要让LLM抽取值或语义检索结果代替统计结果。

### 同节去重不等于同事件去重

Quarry 针对文档章节去重，GridMate 应按经过确认的事件身份与来源关系去重。相似备注不一定代表同一事件，不能仅凭文本相似就合并业务事件。

### 更换检索底座不保证效果提升

Quarry 使用PostgreSQL向量检索与全文检索；GridMate使用Milvus向量检索与BM25。两者不能仅凭都叫“混合检索”就视为等价。即使向量维度相同，不同Embedding模型产生的向量也不能混用。

## 六、建议实施顺序与验收标准

### 阶段0：收尾当前正确性问题

先复核第三次审阅中仍存在的年份改写、部分覆盖、缓存与会话顺序问题。整合Quarry不会自动修好这些问题。

验收：相同问题通过单轮接口和网页聊天入口时，年份与过滤条件一致；部分覆盖有明确提示；同一会话不会因并发形成错序历史。

### 阶段1：增加统一证据对象与查询范围

建议在`app/core/`新增小型证据模型模块，调整`ask.py`、`similar.py`、`tools.py`和`agent.py`之间的数据传递。名称与具体文件拆分可以按实现需要确定，无须复制整套Quarry目录。

验收：统计与案例均有版本、实际范围和来源；冲突不丢失；不支持的条件明确拒绝；模型看见的证据与评审使用的证据一致。

### 阶段2：可靠数据发布与回退

改造事件语料和向量构建流程，增加版本清单、新集合构建、校验后切换与缓存刷新。

验收：重复构建不增加重复事件；缩小数据集不残留旧事件；向量生成或入库失败时旧版本仍可查询；统计和检索不会静默使用不同数据版本。

### 阶段3：检索不足信号与固定评测

用停电场景标签校准检索不足判断，完善逐题记录与整合前后对比。

验收：明确记录检索相关性、范围遵守、误拒/漏拒、引用正确性和请求耗时；能够解释具体改善和失败案例。题量小时如实称为小规模验证，不外推为业务整体准确率。

### 阶段4：按实际需求决定是否接独立Quarry服务

只有出现长篇故障报告、规程文档、多应用共享检索等明确需求时，再考虑HTTP接入Quarry。

届时保留GridMate统计工具，另加文档证据检索工具，通过Quarry客户端访问服务；先定义业务字段与引用映射，再重新导入与评测。开发环境中两个项目默认都使用8100端口，需配置不同端口。

在当前事件备注较短、样本规模较小的阶段，父子分块、邻块扩展和完整多租户平台不是优先项。

## 七、面试表述建议

在完成并验证前，不要将本方案写成已经实现的能力。完成后，可以按实际成果说明：

> 我围绕停电台账设计了统计与案例检索协同的问答流程。统计采用参数化SQL控制口径，案例检索使用结构化范围约束；参考开源检索平台设计统一证据结构，保留数据版本、来源和冲突信息，并通过固定题集验证范围一致性、索引更新失败回退及回答引用。

需要能回答：为什么保留SQL统计、为什么不直接迁移底座、如何定位到原始记录、如何保证两个工具的数据版本一致、哪些模块参考了已有项目，以及哪些改造和验证由自己完成。

项目区分度主要来自对真实台账问题的处理和可复现证据，而不是新增框架数量。
