# GridMate 停电台账问数 · 评测报告

> 状态：第一版评测已完成。评测集 9 条（6 问数 + 3 相似检索），三指标分开统计，数字用独立参考查询对照。
> 含真实数据字段，本报告不可公开，面试口头讲述即可。

---

## 一、评测设计（为什么这么测）

### 1.1 三指标分开，不混成一个"准确率"

| 指标 | 含义 | 通过标准 |
|---|---|---|
| 接口成功 | 意图识别是否正确解析出模板 | template 匹配期望 |
| 流程执行成功 | 参数校验 + SQL 执行 / 检索是否跑通 | status 匹配期望 |
| 回答事实正确 | 数字是否正确 | 与**独立参考查询**一致 |

一个回答"接口调通了"和"数字算对了"是两回事，混成一个准确率会掩盖问题（比如"接口成功但数字虚高"）。

### 1.2 独立参考查询（关键原则）

**统计答案的标准答案，用不同于被测函数的独立 SQL 写法 / Python 累加重算。** 否则就是"让同一个统计函数既产答案又产标准答案"，等于自己给自己打分。

本评测的独立参考：
- 线路停电次数：`sqlite3` 直连 + 手写 `COUNT(DISTINCT 事件序号)`（不走 query_templates）
- 缺供电量总和：Python 逐行累加（不是 SQL `SUM`）
- 时间段事件数：手写 `>= start AND < end`
- 停电性质种类数：手写 `COUNT(DISTINCT 停电性质)`

## 二点五、数字类扩量评测（26 条，独立参考现算）

冒烟级 9 条证明链路能跑后，扩量到可量化长期准确率的规模。数字类问法的标准答案可用独立参考查询自动算，故批量生成 26 条样例（`ask_samples_extended.json`），评测时**用独立 SQL 现算核对**（不照抄样例里存的答案，生成器/评测器双重独立）。

覆盖 4 个维度、不同取值（高/中/低量级，让样例有区分度）：

| 维度 | 样例数 | 覆盖 |
|---|---|---|
| 线路停电次数 | 8 | 高/中/低次数线路各若干 |
| 供服中心缺供电量 | 8 | 高/中/低缺供电量中心 |
| 时间段事件数 | 8 | 12 个月中随机抽 8 个月 |
| 停电性质占比 | 2 | 不同问法 |

**结果全绿：**

```
接口成功: 26/26
流程执行成功: 26/26
事实正确: 26/26  (独立参考对照)
```

**累计（冒烟 4 数字 + 扩量 26）：问数数字正确 30/30 = 100%。**

### 二点五.1 语义相似类：人工标注框架已搭好，待标注

数字类可自动核对，但「这个事件和 query 是否真相似」是语义判断，机器自评不可信，必须人工标 ground truth。已搭好标注框架：

- `scripts/query/label_similar.py`：对 10 个候选 query 跑检索，打印 top-5 结果（含事件文本）；
- 产出 `tests/data/similar_label_template.json`：10 query × 5 结果 = **50 个待标注项**，标注人填 1(相似)/0(不相似)。

**标注中已肉眼发现一个真实检索质量问题（待量化）：** 具体技术术语 query（"开关跳闸""箱变故障"）的 top-1 重排分只有 0.06~0.08，远低于"计划检修"的 0.97。当时初判是"术语在文本里是伴随现象不是主题词"，但后续定位到真正根因（见下）。

### 二点五.2 修复重排 bug（评测逼出的真实问题）

在做相似检索人工标注时，发现部分 query 重排分异常低，逐行追到 `similar.py` 重排代码，定位到一个真实 bug：

**根因：** 重排阶段漏传了事件正文 `text`，只把 `outage_type`（停电性质）、`voltage_level`（电压等级）、`line_names`（线路名）三个标签字段喂给了 bge-reranker。混合召回靠正文（BM25）能召回对的事件，但重排模型看不到故障对象/原因/处理措施这些真正的语义，只能瞎排。

**修复：** 重排文本拼入 `e.get('text','')`（一行改动）。

**修复前后重排分对比：**

| Query | 修复前 top-1 重排分 | 修复后 top-1 重排分 |
|---|---|---|
| 电缆故障 | 0.62 | 0.96 |
| 开关跳闸 | **0.07** | **0.93** |
| 箱变故障 | 0.06~0.08 | 0.94 |
| 接地故障 | 偏低 | 0.97 |
| 10kV 线路检修 | 0.90 | 0.99 |

"开关跳闸"从 0.07 飙到 0.93，翻了 13 倍——这直接证明之前"术语查不准"的主因是代码漏传正文，而不是"术语是伴随现象、数据本身难检"。

**关于 Precision@5 的诚实说明（评测方法论）：**

修复后重新跑了 10 个 query，Top-5 里**出现了大量旧标签未覆盖的新事件**（30/50 个 event_id 变了）。这意味着**不能拿"修复前"的 ground truth 去评"修复后"的检索结果**——旧标签失效了。

之前冒出的一个"修复后 P@5 反而掉到 0.28"是**假象**：不是检索变差了，而是新事件还没标注、被保守口径全按"不相关"误算。

正确做法是**对修复后的新 Top-5 重新标注一次**（已生成 `similar_label_template_v2.json`，50 项待标），才能得出修复后的真实 P@5。肉眼扫一遍修复后结果，检索质量明显改善：电缆故障 Top-5 全是电缆故障、开关跳闸 Top-5 全含"开关跳闸"且分都在 0.9+、低压分支箱故障 Top-5 全是分支箱相关（0.96+）。

### 二点五.3 修复后重新标注：真实 P@5（AI 初审）

修复后重新跑了 10 个 query 的 Top-5，生成 `similar_label_template_v2.json`，交由 AI 辅助初审逐项标注（`similar_label_ai_review_v2_20261116.json`）。

| 箱变故障 | 2 | 0 · 0 1 1 |
| 计划检修 | 4 | 1 1 1 · 1 |
| 10kV线路检修 | 3 | 1 1 0 1 · |
| 业扩工程 | 4 | 1 1 1 1 · |
| 计划调电 | 5 | 1 1 1 1 1 |

**v1 → v2 对照：**

**三个后续发现（比"重排漏正文"更深，待处理）：**

1. **高分 ≠ 正确对象**：5-3 重排分 0.9889 但其实是"箱变检修"非"线路检修"；3-1 重排分 0.9436 但正文是"分支箱故障"非"箱变本体故障"。重排分是相关度，不能当业务正确性判据——对象/现象/原因/处置动作要分开解释。

2. **事件备注聚合未核验组内冲突**（需修）：`build_event_corpus.py` 按事件序号全局分组、不同备注空格拼接、属性取首个非空值，没有检测组内属性冲突。导致 1-4、6-5、8-2、9-3、9-5、10-2 出现"一个事件混入两段不同作业"的拼接问题。

3. **多样性与脱敏残留**：1-1/1-2 是同一上游故障的不同记录，Query 7 四条备注完全相同；v2 仍含姓名/门牌等未脱敏片段，不能默认已公开脱敏。

## 三、已知边界与失败案例（主动声明，非隐藏）

### 3.1 「停电原因」是歧义问法，置信度卡阈值抖动

**现象：** "停电原因都有哪些、各占多少"这个问法，模型置信度在 0.55~0.6 之间抖动（5 次采样 4 次 0.6、1 次 0.55），恰好压在置信度阈值 0.6 上。

**根因（真实语义边界）：** 台账里的字段叫"停电**性质**"（内部故障/计划施工/计划检修等分类标签，这是 SQL 聚合维度）；而"停电**原因**"在台账语境里更接近"备注说明"里描述的具体故障原因（开关跳闸、电缆故障等），那是 RAG 相似检索的对象，**不是 SQL 聚合维度**。

- 问「停电**性质**」→ 置信度稳定 0.95，正确走 SQL；
- 问「停电**原因**」→ 置信度 0.55~0.6，模型正确识别出歧义并降置信度。

**处理：** 这是系统**正确地识别了真实口径歧义**，不是 bug。评测集用稳定的"停电性质"问法做断言样本；"停电原因"这个歧义问法作为**已知边界**记录——无论它过闸（按性质统计）还是不过闸（让用户确认），系统都没答错数，行为是安全的。

**面试可讲点：** 这正体现了方案里"只有会实质改变答案的歧义才要求用户选择"——系统能区分"性质"（确定性 SQL 维度）和"原因"（模糊语义维度），而不是把两者糊成一个字段。

### 3.2 越界问题兜底到 outage_type_ratio

"帮我查天气"这类越界问题，模型在"不知道查什么"时会兜底选 outage_type_ratio 模板，但 confidence=0，被正确拦截（low_confidence）。行为是对的（拦截），只是模板取值无意义。评测对越界样例只断言"被拦截"，不断言模板精确值。

### 3.3 已知限制（后置项，非缺陷）

- 评测集规模小（9 条），是**冒烟级**验证，证明链路正确性，不足以量化长期准确率。扩量到 30~50 条人工核对是后续工作。
- 相似检索的"正确性"目前只核对了"停电性质是否匹配"，未核对"具体事件是否真的是语义相似"（需要人工标注 ground truth）。
- 相对时间的换算（今年/去年/6月）依赖 prompt 里写死的 `_DATA_YEAR=2025`，换数据年份需同步改。

## 四、结论

停电台账问数的完整链路（数据 → 问数 → 相似检索 → 溯源 → 评测）已闭环。第一版评测证明：

1. **问数数字正确**：4 个有数字的样例全部通过独立参考查询对照，没有"自己给自己打分"；
2. **越界/库外值能正确拦截**：不存在的线路、越界问题都被置信度闸 + 参数校验拦下；
3. **相似检索语义正确**：故障/检修/线路检修三类问法都能召回正确停电性质的事件；
4. **口径歧义被正确识别**："停电原因 vs 停电性质"这个真实语义边界，系统能区分。
