# GridMate 二次代码审阅与优化建议

审阅日期：2026-11-16。对象：当前本地 GridMate 工作目录。本文复核了首次审阅后的代码改动，不覆盖或否认首次审阅时的历史结果。

> **修复状态（2026-11-16 更新）**：本文 10 个问题中，**代码层已全部修复**（问题 1~10），具体改动见各问题条目下方的「✅ 已修复」标注。**数据重建闭环也已执行完成**（问题 5 的「重建衍生数据」+ 问题 8 的「数据更新流程」联动）：原始 Excel → 脱敏 CSV → SQLite → 语料 → Milvus 向量全量重建，`某路器` 受损从 281 条降为 0 条，评测 26/26 重跑全过。重建中暴露并修复了「评测样例硬编码假名」的脆弱点（见「五」末尾新增的『数据重建闭环记录』）。

## 结论

改造后的主线仍值得保留。第一轮修改已解决一些具体问题，但不能据此认定全部修复完成：新增的过滤校验、忠实度重试还存在遗漏；数据重建和向量更新缺乏完整替换机制；评测新旧脚本口径没有统一。每个问题的修复项与验收标准见「五、修复执行清单与验收标准」。

本轮仅审阅并新增文档和复现结果，没有修改业务代码、真实数据库、语料或 Milvus 索引，也没有调用外部模型、Embedding 或 Reranker。

验证方式：本地 SQLite 只读聚合、合成数据、替换模型和向量客户端的模拟调用、FastAPI TestClient 本地接口调用。28 个 Python 文件通过 AST 语法检查；当前未发现 `tests/**/test_*.py`。这不是一次真实模型与 Milvus 的端到端验收。

机器可读证据：[二次审阅复现结果-2026-11-16.json](二次审阅复现结果-2026-11-16.json)。文件只有合成示例和聚合结果，没有原始事件正文、真实身份字段或密钥。

> 证据 JSON 的字段语义约定（引用时勿误读）：`db_aggregate` 下的 `停电起始时间/停电终止时间/电压等级` 等键为**事件内该字段多值（非唯一）的计数**，不是"空值数"或"字段值"——例如 `电压等级: 0` 表示电压等级在事件内无多值冲突（实测该字段 6603 行非空、覆盖全部 2000 事件），`停电起始时间: 608` 表示有 608 个事件该字段在组内非唯一。具体语义见对应问题条目。

### 1. P1：检查器异常时仍放行原答案并写入历史

位置：`app/core/agent.py:123`、`:225`；`app/core/faithfulness.py:64`。

检查器已区分 `faithful / unfaithful / unverified`，但 Agent 只对 `unfaithful` 做处理。`unverified` 会转成 `faithful=False`，同时保持 `degraded=False`，原答案照常返回并进入会话历史。接口还没有保留这个三态字段，前端也无法稳定区分“明确错误”和“检查失败”。

复现：检查器模拟返回 `unverified`，合成答案“停电999次”被原样返回，历史中也有999。

建议：保留显式 `verification_status`，为“未验证”单独制定降级策略。不得把它作为已确认事实写入历史。测试应分别覆盖明确不忠实、检查器超时、关闭自检、重试失败，不能仅测一次否定结果。

### 2. P1：重试后的答案与工具证据不属于同一轮

位置：`app/core/agent.py:131`。

重试重新调用整个 Agent，可能重新选择工具、重新解析过滤条件并获得不同结果，但检查器仍使用第一次的 `tool_results`。即使重试通过，代码只更新答案和消息，不更新 `tool_results`、`tool_calls`，返回的溯源会互相矛盾。

复现：第一轮工具返回“1次”，第二轮工具返回“2次”。第二次检查器收到的仍是“1次”；模拟检查通过后，响应中的 `messages` 为新证据，`tool_results` 仍为旧证据。模拟通过只用于验证数据同步，不代表真实评委会接受矛盾答案。

建议优先采用“固定已核验工具证据，只重写答案”，把失败原因带入重写提示；若确实允许重跑工具，就从当前轮消息重新收集证据和工具调用，并原子更新整份结果。相同答案也应区分是否基于相同证据，不宜仅凭字符串相同跳过校验。

### 3. P1：过滤校验仍不完整，既会错答，也会HTTP 500

位置：`app/core/ask.py:326`、`:362`、`:386`。

已复现三个独立缺口：

- `line_outage_count + supply_center` 未被 `_collect_filters()` 收集，校验通过后丢弃中心。“线路32＋供服中心1”真实交集为0次，现有参数转换执行线路全年统计得到8次。
- `supply_center_energy + line_name` 同样丢弃线路，返回整个中心的缺供电量。即使暂不支持，也应明确拒绝。
- 线路/中心模板只填起始或结束日期时，日期函数收到 `None`，抛出 `TypeError`。本地 TestClient 请求复现HTTP 500。
- 时间模板上的可选线路/中心没有词典校验。“线路99999＋6月”通过并返回0次，将“实体不存在”混同于“确实没有事件”。

建议：统一枚举所有非空过滤字段，减去主参数后逐项校验白名单，不要按模板手写漏项分支；时间必须成对出现，先判断空值再检查日期；实体无论作为主参数还是可选过滤，都执行相同词典校验。

### 4. P1：相对年份仍被改写，范围外数据被当作零次

位置：`app/core/ask.py:152`；`app/core/agent.py:50`。

“今年”和“去年”仍都被要求解释成2025。以当前日期2026-11-16为准，这会改变“今年”的含义。“上个月”也没有明确传入参考日期。日期格式合法并不代表查询范围有数据覆盖。

建议：传入明确参考日期，或在界面设置并展示分析年份；区分 `out_of_coverage` 和“覆盖范围内结果为0”。对于没有年份的“6月”，可采用明确显示的数据年份默认值。回答同时说明当前是抽样台账范围。

### 5. P1：脱敏仍损坏故障术语，修代码后还没闭环更新衍生数据

位置：`scripts/data_prep/sample_and_mask.py:156`、`:180`。

当前通过技术词白名单保护“断路器、线路”，但地址正则仍允许没有门牌号、没有地址上下文的普通词。合成验证：

| 输入 | 输出 |
|---|---|
| 断路器故障 | 断路器故障 |
| 线路检修 | 线路检修 |
| 短路故障 | 某路故障 |
| 回路故障 | 某路故障 |
| 开路故障 | 某路故障 |

当前 `event_corpus.jsonl` 仍有36条包含“某路器”的旧受损文本。修复函数不会自动纠正已生成的CSV、SQLite、语料和向量。本轮未连接Milvus，因此其内容是否同步更新仍未知。

建议：收紧地址识别依据，而非无限扩充术语例外。为短路、断路、回路、线路以及真实地址的合成样例建立正反例。修复后按CSV→SQLite→事件语料→向量→评测依次重建并记录数据版本。

### 6. P2：完整检索正文被固定裁成前200字

位置：`app/core/tools.py:115`。

虽然正文现在传给模型了，但重排看到全文，回答模型只看到前200字。当相关故障或处理动作在第二段时，检索排序与答案证据仍会脱节。

复现：合成正文221字，关键“电缆绝缘击穿，已更换”位于末尾，工具输出中完全缺失。当前2000条语料中16条超过200字；这证明有实际触发范围，但不意味着这16条每次查询都会丢关键内容。当前最长正文UTF-8长度为824字节，演示规模下无需如此激进截断。

建议：当前先保留完整事件正文；后续按查询选相关句及上下文，并标注是否截断和来源片段。线路列表同样不宜无提示截前30字。

### 7. P2：事件时间取首值，不能代表事件整体范围

位置：`scripts/query/build_event_corpus.py:69`、`:115`。

当前把事件起止时间取为第一条用户记录中的非空值。数据库中608个事件有不同起始时间、662个有不同结束时间；339个事件的首开始时间不是最早时间，427个首结束时间不是最晚时间。

这不证明原始数据错误：同一事件下不同用户可能分别停送电。问题是合并后抹去了时间差异，呈现出一个没有定义依据的“事件起止时间”，将来做按日过滤也会与用户行统计口径不一致。

建议：保留用户/作业分段时间。如果展示事件整体时间包络，明确为最早开始、最晚结束；如果使用主记录时间，应明确选择规则。不要仅凭组内性质多值就宣称业务上天然多标签，也不要未经核实直接拆分事件ID。

### 8. P2：数据更新流程无法可靠地重复执行

位置：`scripts/query/build_db.py:150`、`:178`；`scripts/query/vectorize_events.py:126`。

SQLite建库仅 `CREATE IF NOT EXISTS + INSERT`，重复导入已有事件会触发主键冲突；各表单独提交，后续导入失败还可能留下部分新表数据。已在内存数据库用合成事件复现第二次导入 `IntegrityError`，未对真实库执行导入。

向量入库按列表下标做主键，只upsert当前行，不删除不再存在的行。模拟客户端中先导入A/B/C，再缩为A，最终仍保留3条。代码层面已复现；本轮未检查真实Milvus是否有残留。

建议：这个2000事件规模采用“新建版本→完整校验→切换”的全量重建较容易说明和维护。SQLite先导入临时库，校验后替换；Milvus使用新集合和别名切换。事件主键应稳定，并校验Embedding数量/维度、数据行数、数据版本，避免 `zip()` 静默截断。切换SQLite时清理进程内词典/分母缓存。

### 9. P2：评测仍存在新旧两套标准

位置：`scripts/eval_ask.py:105`；`scripts/eval_ask_extended.py:27`；`README.md:122`。

旧冒烟评测依然用实际意图参数计算参考值，性质占比也只比较类别数。同一个“完整6月却返回159次”的反例，在旧脚本中通过，在扩展脚本中失败。

扩展脚本目前校验主参数和数字，但尚未完整比较组合过滤条件；将来新增组合题时，如果漏掉过滤刚好不改变结果，也会漏检。当前评测也主要调用 `ask()`，没有覆盖Agent重试、工具证据截断和HTTP错误。

建议：两份评测共用独立预期条件和判定器，完整比较指标及过滤集合，新增本报告反例；按数据版本保存标准答案。README 的30/30应标明版本与范围，修复后重测，不能沿用旧结论证明新链路。生成前selfcheck仍未在主链路实现，应删除对应宣传或真实补齐。

### 10. P2：Git忽略规则还漏了包含事件正文的标注模板

位置：`.gitignore:24`；`tests/data/similar_label_template.json`；`tests/data/similar_label_template_v2.json`。

当前已忽略masked目录与AI review文件，但两份“template”文件各含50个非空text字段，均未命中忽略规则。模板文件名不代表它只有空结构。

本次没有输出这些正文，也没有判断每一条都含个人信息，更没有发现它们已经公开的证据。但按项目“真实数据仅本地”的约定，这些文件不能因名称是模板就随代码提交。

建议：数据文件按内容而非文件名分类。公开示例用合成文本；真实候选正文、标注和含原文的报告统一放到排除路径，提交前检查暂存区。

## 三、值得做但不必扩张架构的优化

### A. 先降低单次请求的成本和最长等待时间

网页一次普通问数可能依次经历：指代消解→Agent选工具→问数工具再次解析意图→Agent生成→忠实度检查。现在忠实度重试还会重跑整个Agent，没有将失败原因反馈给模型，容易重复开销。

建议：无历史时跳过指代消解；工具直接接收结构化指标和过滤条件，复用现有校验与SQL执行；忠实度不通过时优先固定证据重写。为整次请求设总超时和工具调用上限，同时记录各阶段耗时、调用次数与Token用量。此处是结构性成本分析，本轮没有真实延迟测量。

### B. 修好同一会话的并发顺序

位置：`app/static/index.html:204`、`:240`；`app/core/agent.py:213`；`app/core/memory.py:20`。

按钮禁用后，Enter仍直接调用sendMsg；函数没有busy检查。后端也没有同一session串行化。连续提问可在上一轮未完成时读取不完整历史，返回顺序还可能与提问顺序相反。

建议：前端增加统一busy状态，后端按session串行处理或拒绝并发。历史加最大轮数和过期时间；当前只是读取最近若干轮，实际列表仍不断增长。本项来自源码检查，本轮未做浏览器并发实测。

### C. 统计与检索共享过滤范围，增加“证据不足”的出口

`similar.py` 仍无线路/中心/时间硬过滤参数。不能用向量相似度代替条件过滤；“这条线路6月的案例”不能只靠把这些字写入query。

建议复用已验证的过滤结构，并按最终确认的事件时间口径过滤。检索结果还应区分“有候选”和“足以支持回答”；阈值需用负例校准，不能直接拍一个重排分。也不要将Top-K条数说成故障发生总次数。

### D. 补可复现启动与轻量回归，比加新框架更有价值

公开仓库排除真实数据后，README需要提供合成演示数据、依赖同步、SQLite初始化、Milvus初始化命令。健康检查区分进程存活和依赖就绪；测试覆盖本文已复现分支。模型/HTTP/Milvus客户端在应用退出时关闭，Reranker尽量复用连接池。单用户本地演示不必因此引入分布式会话或任务队列。

## 四、推荐下一轮顺序

1. 修复过滤校验、单边时间500、检查器异常和重试证据错配，先用模拟回归保证分支正确。
2. 明确日期与事件时间口径，修复脱敏并打通可重复的数据重建流程。
3. 统一评测，补完整链路的小规模验收题；修正README和面试表述。
4. 最后优化重复模型调用、超时、会话并发和连接复用。

无需重写整个项目。重点是让同一个问题的用户条件、SQL结果、检索范围、回答证据和评测预期保持一致。

## 五、修复执行清单与验收标准

> 本节把上面 10 个问题落成**可勾选、可测试**的执行项。每一项都给出「怎么算修好」的验收断言，修复时逐条对照，避免"改了但没验证"。
