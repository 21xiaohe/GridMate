## 1. 发布中途失败导致新旧数据混用

**原问题**

原脚本先替换正式 SQLite，再覆盖语料，最后构建向量并更新清单。如果向量失败，数据库已经是新版，向量仍是旧版，但两者展示同一个旧版本号。

**现在的实现**

- 每次生成唯一版本号。
- 数据库及语料写入 data/masked/versions/<版本号>/。
- 向量写入 outage_events_<版本号>，不覆盖旧集合。
- 验证 SQLite 完整性、数据库与语料的事件 ID 集合、语料及向量条数、向量集合中的事件 ID/正文，以及向量查询可用性。
- 清单保存各产物路径、SHA-256、集合名、事件 ID 集合摘要、向量模型信息和声明的数据范围。
- 全部完成后，使用一次 os.replace 切换 version.json。
- 一次回答通过 ContextVar 固定 DatasetSnapshot 和 request_id；并行工具调用及自检重试继续使用同一版数据。
- 发布锁防止两个发布/回滚进程同时切换。旧版本保留；回滚前重新核对目标版本。

**验证**

分别在数据库、语料、向量和清单切换阶段注入失败，旧清单及旧产物保持不变。请求处理中切换新版本后，该请求仍读旧快照；新请求才可读取新版本。修改已发布文件会触发摘要校验失败。

**面试表达**

> 我发现给两个工具返回相同版本号，并不能证明它们读的是同一份数据。我改成按版本构建独立产物，所有验证完成后只切换一个清单；请求开始时固定快照。这样发布失败不会让新数据库和旧索引混用，也保留了回滚路径。

实现：[versioning.py](C:/Users/xiaohe/WorkBuddy/实习/GridMate/app/core/versioning.py)、[publish.py](C:/Users/xiaohe/WorkBuddy/实习/GridMate/scripts/query/publish.py)。

## 2. 向量切换仍然先删除旧集合

**原问题**

原先虽然先写 staging，但最后仍是 drop 旧集合再 rename 新集合。重命名失败时正式集合已经不存在。

**现在的实现**

构建函数只创建独立版本集合。已有同名集合则拒绝覆盖；不执行 drop 或 rename。读回验证及向量查询完成后，将集合名交给完整发布流程激活。

失败可能留下未激活的目录和集合，旧版服务继续使用原产物。这些残留不自动删除，避免误清理仍有请求使用的版本。

**验证**

写入、加载、内容核对、向量查询分别失败时，旧集合仍保留。真实 Milvus 中还验证了新集合 schema、中文分词/BM25 配置、索引、读回及混合召回。测试只创建随机名称的 smoke 集合，结束后已清理。

**面试表达**

> staging 只能保护构建阶段，不能保证最终切换安全。我去掉了“先删旧集合”的步骤，用不可变集合和清单指针切换；失败最多留下未激活的新集合，不会破坏旧服务。

实现：[vectorize_events.py](C:/Users/xiaohe/WorkBuddy/实习/GridMate/scripts/query/vectorize_events.py)。

## 4. 统计与案例时间口径不一致

**原问题**

统计根据用户记录的停电开始时间筛选，检索根据整个事件包络与区间重叠筛选。当前台账 6 月分别对应 160 和 161 个事件。

**现在的实现**

默认 record_start：先在同一 SQLite 快照中，按线路、供服中心、开始时间求符合条件的事件 ID，再作为向量召回硬过滤。线路与时间条件作用于同一用户记录，避免不同记录的条件被错误拼接。

保留显式 event_overlap：按整个事件包络重叠检索，证据和回答要求说明采用了不同时间口径。统计举例使用默认口径及同样的过滤条件。

部分时间覆盖时，不仅显示裁剪范围，SQL 本身也执行裁剪后的区间。覆盖依据来自项目声明或发布参数，不能用最早/最晚事件日期推断数据完整性。当前仍声明为抽样台账。

**验证**

- 同日事件、跨月事件、多线路事件有独立合成样本。
- 真实台账只读核对：6 月统计 = 160，默认检索合格集合 = 160，显式重叠集合 = 161。
- 未增加相关度分数拒答阈值。

**面试表达**

> “6 月停电”可能指 6 月开始，也可能指 6 月期间仍在停电。我把口径作为显式字段。需要给统计结果举例时，先从统计数据库得到同口径事件集合，再进行语义排序，避免数字和案例的范围不一致。

## 5. 证据对象转成字符串后丢失元数据

**现在的实现**

- 工具采用 content_and_artifact，同时返回模型文本及结构化 ToolEvidence。
- 统计证据保留来源表、模板、实际执行参数、结果行、比例分母和多标签信息。
- 案例证据保留事件 ID、users 源记录 ID、正文、属性、冲突和召回/重排分数。
- 两类证据都保留 request_id、数据版本、版本校验状态、请求范围、实际范围、覆盖依据和告警。
- Agent 保存 artifact，并在 API 的 evidence 字段提供结构化证据。
- 忠实度检查先从 artifact 重新渲染，核对它与回答模型收到的工具文本一致，再进行模型检查。缺失或不一致时返回 unverified。
- 网页可展开查看来源和查询范围。

**验证**

实际 LangChain 工具调用返回 artifact；实际 create_agent 图中的两个并行工具调用共享 request_id 和版本。API 测试能够读取源记录 ID。篡改文本而不改 artifact 会被标记为未验证，忠实度失败重试也不会复用上一轮证据。

**面试表达**

> 我把证据作为业务对象保留下来，给模型的文本只是这个对象的一种展示形式。回答、自检、接口展示都来自同一份证据，后续排查可以定位到数据版本、统计条件和原始记录。

边界：源记录 ID 只在对应数据版本中有意义；不能跨版本直接把相同的自增行 ID 当成同一条记录。统计证据以来源表、模板和参数定位聚合结果，不把全量用户记录塞进回答。

实现：[evidence.py](C:/Users/xiaohe/WorkBuddy/实习/GridMate/app/core/evidence.py)、[agent.py](C:/Users/xiaohe/WorkBuddy/实习/GridMate/app/core/agent.py)、[faithfulness.py](C:/Users/xiaohe/WorkBuddy/实习/GridMate/app/core/faithfulness.py)。

## 6. 没有数据与处理失败混为一谈

现在区分：

| 状态 | 含义 | 是否可以说没有事件 |
| --- | --- | --- |
| out_of_scope | 请求时间完全超出台账声明范围 | 不可以，只能说没有覆盖 |
| empty | 在有效范围内未召回候选 | 只能描述本次检索结果，不能外推现实不存在 |
| processing_error | Embedding、召回或重排未完成，包括重排空返回、无效索引/分数 | 不可以，应该说明无法判断 |
| 正常结果 + has_conflict | 有命中，但部分事件属性有冲突 | 保留案例和冲突说明 |

未知线路/供服中心属于参数问题，不冒充“合法范围内没有事件”。

**面试表达**

> 空列表可能来自数据范围外、召回没命中或重排异常，用户应对它们作出的判断不同。我将这些状态分开处理，避免把系统失败包装成业务事实。

实现：[similar.py](C:/Users/xiaohe/WorkBuddy/实习/GridMate/app/core/similar.py)。

## 7. 评测能生成报告，却不能可靠判断通过

**现在的实现**

- 一次检索返回重排前候选、最终结果及阶段耗时；不再用两次完整检索冒充两个处理阶段。
- 用真实重排前候选计算已标注正例召回漏检，名称与系统拒答区分。
- 范围检查通过原始台账按相同口径得到事件集合，避免把时间戳截断成日期。
- 来源检查对照同版本语料的事件 ID、正文和关键属性，不再只检查字段非空。
- 每题明确 pass/fail/unverified。每题异常都会保留结果并继续，全部报错不能返回成功。
- 退出码：0 全部通过；1 至少一题失败；2 没有失败但仍有未验证项。
- 没有标签的返回结果记为相关性未验证；旧数据布局也不能记作跨库一致性已通过。
- 每次生成独立运行目录，保存代码文件摘要、Git 提交及脏状态、模型名、检索配置、数据/题集/标注版本和逐题结果。
- 支持配置相符的基线比较。范围外题明确要求 out_of_scope，未知实体题要求参数拒绝。

**验证**

7 题全部接口报错时退出码为 1 且保留完整报告；有候选但排序靠后的相关事件不再误报为未召回；同日事件范围检查正确；未标注结果退出码为 2；多次运行不会覆盖报告。

**面试表达**

> 评测脚本本身也可能出错。我先明确每个指标测的是召回、排序还是来源一致性，再用故障注入检查评测器能否正确失败。生成一份报告不等于系统通过验收，缺少标注也不能默认算对。

边界：AI 初审标签仍未人工全量复核；本次没有重新运行真实模型固定集。因此本次测试通过数不能换算成检索准确率或回答准确率。来源匹配检查也不等于验证生成回答中每一句引用。

实现：[eval_fixed_set.py](C:/Users/xiaohe/WorkBuddy/实习/GridMate/scripts/query/eval_fixed_set.py)。

```powershell
.venv/Scripts/python.exe -m scripts.query.publish --rollback <版本号>

.venv/Scripts/python.exe -m scripts.query.eval_fixed_set --top-k 5
```

范围过滤当前使用 SQLite 求事件 ID 后传入 Milvus，适合当前约 2,000 个事件的规模。扩展到大规模数据时，需要评估预筛选成本、表达式长度和更合适的索引结构。
